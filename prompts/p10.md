==================================================
CRITICAL ARCHITECTURAL DECISION
==================================================

Do NOT automatically replace every legacy component with a native Streamlit equivalent.

Evaluate each component individually.

For example:

circular_score()
----------------
Determine whether:

A. st.metric is sufficient
B. st.progress is sufficient
C. st.html() with CSS is justified
D. a reusable .cp-ui score component should be created

The correct answer is NOT automatically A.

If the circular score is an important information hierarchy element, preserve the circular visualization using a semantic .cp-ui component and st.html().

Similarly evaluate:

metric_value()
badge_list()
status_banner()
card_open/card_close()
score_comparison()
resume_debate()
job recommendations
etc.

Use native Streamlit widgets for interactive behavior.

Use .cp-ui + st.html() for presentation where native Streamlit does not provide the required visual representation.

==================================================
NO FAKE NATIVE REPLACEMENTS
==================================================

Do NOT downgrade the design merely because a native Streamlit widget exists.

Examples:

Do not replace a meaningful circular score gauge with st.metric
just because st.metric exists.

Do not replace a designed comparison visualization with plain text.

Do not replace semantic cards with dozens of unrelated Streamlit calls.

Use the best tool for the job.

Architecture should be:

Native Streamlit
    ↓
interactive behavior

st.html()
    ↓
static presentation that needs controlled design

CSS tokens
    ↓
visual language

Business modules
    ↓
business logic

==================================================
COMPONENT EXTRACTION RULE
==================================================

This phase is the first point where more complex reusable components may be justified.

However:

DO NOT create components simply because something is long.

Create a component when:

- the visual pattern is reusable
- the component has a clear semantic API
- it reduces duplication
- it belongs to the presentation layer
- it does not contain business logic

Potential candidates:

render_score_gauge()
render_metric()
render_status_banner()
render_score_comparison()
render_skill_badges()
render_result_card()

But decide based on ACTUAL usage.

Do not invent APIs before inspecting the codebase.

==================================================
STREAMLIT BEST PRACTICES
==================================================

Prefer supported Streamlit APIs.

Use:

- st.container()
- st.columns()
- st.tabs()
- st.expander()
- st.button()
- st.metric() where genuinely appropriate
- st.progress() where genuinely appropriate
- st.html() for static controlled HTML

Avoid:

- JavaScript
- custom React
- iframe-based UI
- Tailwind
- arbitrary DOM mutation
- fragile selectors
- generated fake buttons
- HTML controls pretending to be Streamlit widgets
- unnecessary unsafe_allow_html

If st.html() can cleanly handle a presentation requirement, prefer it over unsafe_allow_html.
