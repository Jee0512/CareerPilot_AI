# CAREERPILOT AI
# PHASE 17 — MODERN PRODUCT UI SYSTEM
# AUDIT + IMPLEMENTATION + SELF-VERIFICATION
#
# Phase 16 is complete.
#
# The application now has:
#
#     ONE PRODUCT
#     ONE APPLICATION SHELL
#     ONE NATIVE NAVIGATION MODEL
#     GROUPED SIDEBAR
#     NO LANDING PAGE
#     NO LEGACY UI SYSTEM
#     NATIVE STREAMLIT INTERACTIONS
#
# Phase 17 is different.
#
# We are now moving from:
#
#     ARCHITECTURAL CONSOLIDATION
#
# to:
#
#     PRODUCT-LEVEL UI MODERNIZATION
#
# ================================================================
# CORE RULE
# ================================================================
#
# Do NOT optimize individual pages independently.
#
# First establish the visual system.
#
# Then apply that system consistently across the application.
#
# The target is:
#
#     MODERN
#     PREMIUM
#     CALM
#     PROFESSIONAL
#     INTELLIGENT
#     PRODUCTIVITY-FOCUSED
#
# CareerPilot AI is a college-level product.
#
# Do NOT introduce:
#
#     monetization
#     billing
#     subscriptions
#     pricing
#     enterprise features
#     fake analytics
#     fake user accounts
#     unnecessary dashboards
#
# Focus entirely on the actual CareerPilot use case.
#
# ================================================================
# IMPORTANT ARCHITECTURAL PRINCIPLE
# ================================================================
#
# React and Streamlit Components V2 are NOT forbidden.
#
# They are also NOT automatically required.
#
# Make the decision based on the actual UI requirements.
#
# Follow current official Streamlit documentation and recommendations
# whenever evaluating Streamlit architecture.
#
# Prefer native Streamlit when it provides the required UX cleanly.
#
# Use st.html() for presentation where appropriate.
#
# Use ui/components.py for genuinely reusable presentation.
#
# Consider Components V2 when a component genuinely requires:
#
#     browser-side state
#     richer client-side interaction
#     JavaScript behavior
#     bidirectional communication
#     custom frontend behavior
#
# Consider React + TypeScript only when a real frontend application
# architecture is justified.
#
# NEVER introduce React merely because it looks modern.
#
# NEVER avoid React merely because the current application uses Streamlit.
#
# Choose based on evidence.
#

# ================================================================
# PART 17 — COMPONENT V2 / REACT DECISION
# ================================================================
#
# During implementation, explicitly identify UI requirements that may
# exceed native Streamlit.
#
# Examples:
#
#     rich resume editor
#     interactive resume diff
#     sophisticated drag/drop
#     advanced interactive visualizations
#     complex client-side state
#     highly interactive interview experience
#
# For every such requirement:
#
#     Native Streamlit sufficient?
#     st.html sufficient?
#     ui/components.py sufficient?
#     Components V2 useful?
#     React useful?
#
# If native Streamlit is sufficient:
#
#     use it.
#
# If Components V2 provides a clearly superior supported solution:
#
#     it is permitted.
#
# If React is genuinely justified:
#
#     it is permitted.
#
# BUT:
#
# Do not migrate the whole application to React merely because one
# component requires React.
#
# Establish a clean integration boundary.
#
# ================================================================

#

#
#     tokens.css

#

#     obsolete tokens

#
#     tokens
#     semantic classes
#     scoped styles
