# CAREERPILOT — ARCHITECTURE ADDENDUM
# PHASE 0.5 — UI BOUNDARY & SCALABILITY AUDIT

This document is an ADDENDUM to the previously provided
"CareerPilot AI — Master Architecture & UI Implementation Specification".

It does NOT replace the master specification.

It clarifies how the UI architecture must be decided before we proceed beyond routing.

IMPORTANT:

The current task is NOT to build the complete UI.

The current task is to determine the correct boundary between:

1. Native Streamlit
2. st.html()
3. Streamlit Components v2
4. React/TypeScript
5. Tailwind CSS
6. Plain CSS/design tokens

The goal is to build CareerPilot as a scalable Streamlit-first product without either:

A. turning Streamlit into a giant CSS hack

OR

B. unnecessarily turning the entire application into a React frontend.

============================================================
# 1. ARCHITECTURAL PRINCIPLE
============================================================

The governing principle is:

> USE THE SIMPLEST TECHNOLOGY THAT CAN SOLVE THE REQUIREMENT CORRECTLY.

Do NOT select a technology because it is fashionable.

Do NOT select a technology because it is already installed.

Do NOT select a technology merely because it is technically possible.

Do NOT introduce React/Tailwind/Components v2 unless there is a concrete requirement.

Do NOT force complex UI into Streamlit if Streamlit cannot provide the required interaction cleanly.

Every UI element must be assigned to the simplest appropriate layer.

============================================================

CareerPilot remains a Streamlit application.

============================================================
# 4. UI DECISION MATRIX
============================================================

For EVERY major UI component, classify it using this decision tree.

------------------------------------------------------------
LEVEL 1 — NATIVE STREAMLIT
------------------------------------------------------------

Use native Streamlit when the component needs:

- Python interaction
- session state
- forms
- uploads
- downloads
- simple actions
- text input
- textarea
- radio
- select
- checkbox
- tabs
- progress
- loading state

Examples:

- Resume uploader
- JD textarea
- JD URL input
- Analyze button
- Optimize button
- Download button
- Interview answer input

DO NOT fake these with HTML/JavaScript.

------------------------------------------------------------
LEVEL 2 — st.html()
------------------------------------------------------------

Use st.html() when the component is primarily PRESENTATIONAL.

Examples:

- static card
- score display
- badge
- visual metric
- static comparison
- decorative section
- visual status
- typography block
- non-interactive diagram

The component must not require Python event communication.

Prefer st.html() over expanding unsafe_allow_html=True.

------------------------------------------------------------
LEVEL 3 — COMPONENTS V2
------------------------------------------------------------

Use Streamlit Components v2 when a component needs:

- frontend interaction
- client-side state
- custom browser behavior
- JavaScript events
- complex interaction
- rich visual manipulation
- advanced visualization
- drag/drop
- rich text editing
- complex custom controls

Before choosing Components v2, document why:

Native Streamlit is insufficient.

st.html() is insufficient.

The component requires actual frontend capabilities.

------------------------------------------------------------
LEVEL 4 — REACT / TYPESCRIPT
------------------------------------------------------------

React/TypeScript is allowed ONLY inside a Components v2 implementation where it provides meaningful value.

Do NOT introduce React at the application level.

Do NOT rewrite Streamlit pages as React.

Do NOT create a separate React application.

------------------------------------------------------------
LEVEL 5 — TAILWIND
------------------------------------------------------------

Tailwind is allowed ONLY where a custom frontend component actually benefits from it.

Tailwind is NOT required for the Streamlit application itself.

Do not install Tailwind just to style:

- st.button
- st.text_input
- st.text_area
- st.file_uploader
- st.tabs
- st.download_button

Use Streamlit's theme and carefully scoped CSS for native widgets.

If a Components v2 frontend is created and Tailwind improves that frontend's maintainability, Tailwind may be used there.

============================================================
# 5. DO NOT MAKE A GLOBAL TAILWIND DECISION YET
============================================================

The previous architecture discussion established:

- Remove the Tailwind CDN.
- Do not use Tailwind CDN as the application's global styling mechanism.
- Do not install Tailwind for the initial Streamlit design system.

That decision remains.

However:

DO NOT interpret this as:

"Tailwind can never be used."

The correct rule is:

> Tailwind is a component-level frontend technology, not a requirement of the Streamlit application.

If a future Component v2 genuinely benefits from Tailwind, evaluate it then.

============================================================
# 13. STREAMLIT NATIVE WIDGET STYLING
============================================================

Native Streamlit widgets remain native.

Do not recreate them.

Use:

1. Streamlit theme
2. Streamlit-supported configuration
3. minimal CSS
4. stable selectors

Avoid unnecessary:

[data-testid="..."]

selectors.

If an internal selector is absolutely necessary:

Document:

- selector
- reason
- Streamlit version tested
- potential upgrade risk

============================================================
# 14. CUSTOM HTML
============================================================

Use st.html() for static presentation.

Do not use custom HTML to create fake interactive Streamlit widgets.

Do not create HTML buttons that are expected to call Python.

Do not build a JavaScript application inside st.html().

If interaction becomes necessary, evaluate Components v2.

============================================================
# 16. REACT RULE
============================================================

React is NOT the application framework.

React may exist only inside an isolated Component v2 package.

If React is introduced, it must not create:

- a second routing system
- a second application state system
- a second backend
- duplicate business logic

Streamlit remains the application orchestrator.

============================================================
# 17. TAILWIND RULE
============================================================

Tailwind is NOT the global CSS system.

If Tailwind is eventually used:

It must be isolated to the frontend component that needs it.

Do not create a global Tailwind layer that competes with Streamlit.

Do not use Tailwind CDN.

Do not inject Tailwind scripts into Streamlit.

============================================================
# 21. STATE
============================================================

Keep session state.

Do not introduce:

- Redux
- Zustand
- React state as application state
- database
- global Python singleton state

A Component v2 may have local frontend state for presentation/interaction, but authoritative application data remains in Streamlit/Python.

============================================================
# 22. CACHING
============================================================

Use st.cache_resource for expensive reusable resources.

Examples:

- SentenceTransformer
- spaCy models

Do not automatically cache Gemini outputs.

Before caching AI responses, evaluate:

- privacy
- cache sharing
- cache lifetime
- cache invalidation
- correctness
- API cost

============================================================

- Streamlit remains the application platform.
- Pages are independently maintainable.
- Navigation is native.
- Session state remains reliable.
- Business logic remains isolated.
- Native widgets remain reliable.
- Static presentation can use st.html().

- React can be introduced locally if genuinely necessary.
- Tailwind can be introduced locally if genuinely useful.
- There is one visual design system.
- There is no Tailwind CDN.
- There is no giant CSS hack.
- There is no unnecessary frontend rewrite.
