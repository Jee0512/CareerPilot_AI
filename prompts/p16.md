# ================================================================
# CORE ENGINEERING PRINCIPLE
# ================================================================
#
# Always choose the BEST PRACTICE for the actual problem.
#
# Do NOT make architectural decisions simply because:
#
#     "we already use Streamlit"
#     "we don't want React"
#     "we don't want Components V2"
#     "custom UI is harder"
#
# Likewise, do NOT introduce technology simply because:
#
#     "React is modern"
#     "Components V2 is newer"
#     "this would look better in React"
#
# Architecture must be evidence-driven.
#
# For every significant technical decision:
#
# 1. Inspect the current repository.
# 2. Check the current official Streamlit documentation/recommendations
#    when the decision concerns Streamlit capabilities or architecture.
# 3. Prefer established best practices used by experienced developers.
# 4. Consider maintainability, accessibility, responsiveness,
#    performance and complexity.
# 5. Choose the simplest architecture that properly satisfies the
#    actual requirement.
#
# React, TypeScript, Streamlit Components V2 and other technologies are
# ALLOWED if they are genuinely justified.
#
# They are NOT mandatory.
#
# They are NOT forbidden.
#

# ================================================================
# PART 11 — REACT / COMPONENTS V2 DECISION
# ================================================================
#
# IMPORTANT:
#
# DO NOT automatically conclude:
#
#     "React is unnecessary."
#
# DO NOT automatically conclude:
#
#     "Components V2 is unnecessary."
#
# The modernization phase may expose requirements that the current
# architecture cannot satisfy elegantly.
#
# Therefore perform a real feasibility check.
#
# For each advanced UI requirement ask:
#
# 1. Can native Streamlit implement it cleanly?
# 2. Can st.html() implement presentation-only behavior?
# 3. Can ui/components.py provide the reusable presentation?
# 4. Does the feature require browser-side state?
# 5. Does it require JavaScript?
# 6. Does it require bidirectional communication?
# 7. Does it require complex client-side interaction?
# 8. Does it require drag/drop?
# 9. Does it require rich text editing?
# 10. Does it require real-time interaction?
# 11. Does it require custom browser APIs?
# 12. Does it require interaction patterns Streamlit does not support well?
#
# THEN:
#
# If native Streamlit is clearly sufficient:
#
#     use native Streamlit.
#
# If Components V2 is genuinely beneficial:
#
#     Components V2 IS ALLOWED.
#
# If React + TypeScript is genuinely beneficial:
#
#     React IS ALLOWED.
#
# But:
#
#     DO NOT introduce either merely for aesthetics.
#
# If React or Components V2 is required for a specific feature:
#
# document:
#
# - exact feature
# - why native Streamlit is insufficient
# - why the chosen technology is appropriate
# - current official Streamlit guidance supporting the approach
# - maintenance cost
# - accessibility implications
# - performance implications
# - integration boundary
#
# Do not rewrite the entire application in React simply because one
# component needs richer frontend behavior.
#
# ================================================================

#
#     st.navigation()

#     st.container()
#     st.columns()
#     st.tabs()
#     st.form()
#     st.file_uploader()
#     st.text_input()
#     st.text_area()
#     st.button()
#     st.link_button()
#     st.download_button()
#     st.html()
#
# Use native widgets for actual interaction.
#
# Use HTML/CSS for presentation only.
#
# Never create fake interactive controls with HTML when a native
# Streamlit control exists and is appropriate.
